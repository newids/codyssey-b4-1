## A. 핵심 6문항 (과제 목표 1:1)

### A1. SSH 포트 변경과 Root 원격 접속 차단이 왜 "기본 보안"인가?
- 인터넷에 열린 22 포트는 수 분 안에 자동 스캐너·봇넷의 **브루트포스 대상**이 된다. 포트를 20022 로 옮기면 "보안 by obscurity" 라 근본 방어는 아니지만, **무차별 자동 공격 트래픽의 대부분을 걸러** 로그 소음과 CPU 낭비를 줄이고 진짜 공격을 눈에 띄게 한다.
- `root` 는 **계정명이 이미 알려진 최고 권한** 계정이다. 공격자는 비밀번호 하나만 맞히면 끝이다. `PermitRootLogin no` 로 막으면 공격자는 (1) 존재하는 일반 계정명을 알아내고 (2) 그 비밀번호/키를 뚫고 (3) 다시 sudo 권한까지 얻어야 한다. 단계가 늘고 **누가 로그인해 무엇을 했는지 감사 추적**도 가능해진다(root 직접 로그인은 책임 소재가 사라진다).
- 둘 다 설정 한 줄로 끝나는 비용 대비 효과가 큰 조치라 "기본"이다. 다음 단계는 비밀번호 인증 금지(키 전용), fail2ban, MFA.
- 검증: `sshd -T | grep -Ei '^(port|permitrootlogin)'`(유효 설정), `ss -tulnp | grep sshd`, `ssh -p 20022 root@host` 가 거부.

### A2. "필요 포트만 허용"하는 방화벽 정책은 어떻게 구성하고 검증하는가? (UFW 선택 이유)
- 원칙: **기본 거부(default deny incoming) + 명시 허용(allow list)**. 열린 포트 = 공격 표면이므로 서비스에 꼭 필요한 20022/tcp(SSH), 15034/tcp(앱)만 연다. 아웃바운드는 패키지 설치·업데이트를 위해 허용.
- 구성: `ufw default deny incoming` → `ufw default allow outgoing` → `ufw allow 20022/tcp` → `ufw allow 15034/tcp` → (기존 22/OpenSSH 규칙 삭제) → `ufw enable`.
- 검증: 서버 안에서 `ufw status verbose`(Status: active, 규칙 2줄), 밖에서 `nc -zv host 20022`(open), `nc -zv host 22`(timeout/refused), `nmap -p 22,20022,15034 host`.
- UFW 를 고른 이유: Ubuntu 기본, 규칙 문법이 단순해 **증빙 가독성**이 좋다. firewalld 는 zone/service 개념이 있어 RHEL 계열에서 표준. 둘 다 결국 netfilter(iptables/nftables) 프론트엔드.
- 주의: 원격 작업 중이면 **allow 20022 → enable → 새 터미널로 확인 → 기존 세션 종료** 순서. 클라우드면 보안그룹도 열어야 한다.

### A3. 역할 기반 계정/그룹과 ACL 로 "공유 디렉토리"와 "보안 디렉토리"를 분리하는 이유는?
- **역할 분리**: admin(운영·cron 실행), dev(스크립트 작성), test(QA). 사람이 아니라 역할에 권한을 붙이면 인원이 바뀌어도 정책은 유지된다.
- **두 그룹**: `agent-common`(세 명 전부) 은 협업에 필요한 `upload_files` 를 공유. `agent-core`(admin, dev) 만 `api_keys` 와 로그에 접근. QA 는 키·로그를 볼 필요가 없으므로 **최소 권한**. 키가 유출되면 범인 후보가 2명으로 줄고, test 계정이 뚫려도 비밀은 안전하다.
- **왜 ACL 까지?** 전통 권한은 "소유자/그룹 하나/기타" 세 칸뿐이다. 한 디렉토리에 **두 그룹 이상**에 다른 권한을 주거나, 상위 디렉토리에 "통과만(x)" 같은 세밀한 권한을 주려면 `setfacl` 이 필요하다. 또 `default ACL` 로 **새로 만들어지는 파일에 정책을 상속**시킬 수 있다(setgid 와 함께).
- 구현 포인트: `o::---` 로 기타 사용자 완전 차단, setgid(2770) 로 그룹 유지, `/home/agent-admin` 과 `$AGENT_HOME` 에는 common 에 `--x` 만 줘서 upload_files 까지 **통과는 되지만 목록 조회/삭제는 불가**.
- 검증: `id`, `getent group`, `ls -ld`(`+`, `s`), `getfacl`, 그리고 **실제로** `su - agent-test -c 'cat key'` 가 거부되는지.

### A4. 환경 변수(AGENT_HOME 등)로 실행 환경을 고정하는 이유와 검증 방법은?
- **코드와 설정의 분리**: 경로·포트를 코드에 박으면 서버마다 소스를 고쳐야 한다. 환경 변수로 주입하면 같은 바이너리를 개발/운영에서 그대로 쓴다(12-factor "Config").
- **일관성**: 앱, 사람(셸), cron, monitor.sh 가 **같은 값**을 보게 한다. `/etc/profile.d/agent-env.sh` 한 곳에서 관리하므로 "앱은 /var/log/agent-app 에 쓰는데 모니터는 다른 곳을 본다" 같은 불일치가 사라진다.
- **명시적 실패**: 앱이 `[2/5] Verifying Environment Variables` 에서 누락을 잡아 준다. 기본값에 조용히 의존하면 장애 때 원인을 못 찾는다(`AGENT_LOG_DIR` 은 기본값이 있어도 "지정 권장"인 이유).
- 검증: `su - agent-admin -c 'env | grep ^AGENT_'` 5줄, 앱 `[2/5] [OK]`, cron 줄에서 `. /etc/profile.d/agent-env.sh` 명시. 함정: `/etc/profile.d` 는 **로그인 셸**에서만 읽히므로 `su -`(대시) 를 쓰고 cron 에서는 직접 source.

### A5. 쉘 스크립트로 프로세스/포트/리소스를 수집해 로그로 남기고 운영 문제를 추적하는 흐름은?
1. **살아 있는가** — `pgrep -f 앱이름`(프로세스), `ss -tlnH | grep :15034`(포트 LISTEN). 프로세스는 있는데 포트가 없으면 "기동 중 멈춤/바인드 실패", 포트는 있는데 프로세스명이 다르면 "엉뚱한 프로세스 점유". 둘 다 봐야 한다. 실패는 **exit 1** 로 알려 상위(cron·알림 시스템)가 반응하게 한다.
2. **건강한가** — 방화벽 상태, CPU(`/proc/stat` 델타), MEM(`/proc/meminfo` MemAvailable), DISK(`df /`). 임계값(20/10/80%) 초과는 **경고만** 한다. 서비스는 살아 있으므로 종료 코드로 "죽었다"고 거짓 신호를 내면 안 된다.
3. **기록** — 한 줄 고정 포맷 `[시각] PID CPU MEM DISK` 로 append. 고정 포맷이라 `grep`/`awk` 로 바로 집계된다(report.sh).
4. **추적** — 장애 신고가 오면 `grep '2026-02-25 14:0' monitor.log` 로 그 시각 전후의 추세(CPU 가 서서히 올랐는가, PID 가 바뀌었는가=재시작, 디스크가 찼는가)를 본다. `monitor.error.log` 에는 Health Check 실패 시각이 남아 **언제부터 죽었는지** 알 수 있다. 미션 서문이 말한 "로그가 없으면 감에 의존" 을 없애는 것이 목적.

### A6. crontab 으로 주기 실행시키는 방법과 로그 보존 정책(압축/삭제)이 필요한 이유는?
- `crontab -e`(agent-admin) 에 `* * * * * . /etc/profile.d/agent-env.sh; $AGENT_HOME/bin/monitor.sh >/dev/null 2>>…/monitor.cron.log`. 다섯 필드 = 분 시 일 월 요일, `*` 는 매번. cron 은 PATH 가 최소이고 로그인 환경이 없으므로 **절대경로 + 환경 파일 source** 가 필수. 확인은 `crontab -l`, `grep CRON /var/log/syslog`, 1~2분 뒤 로그 줄 수 증가.
- 실행 계정이 agent-admin 인 이유: 운영 역할이며 `agent-core` 소속이라 750 스크립트를 실행하고 로그 디렉토리에 쓸 수 있다. root cron 은 스크립트 버그가 시스템 전체를 망칠 수 있어 피한다.
- **보존 정책이 필요한 이유**: 매분 한 줄이면 하루 1,440줄, 디스크는 유한하다. 로그가 디스크를 채우면 **앱이 로그/업로드를 못 써서 모니터링이 장애를 만드는** 역설이 생긴다. 또 오래된 로그는 검색 속도를 떨어뜨리고, 보관 의무(감사)와 삭제 의무(개인정보)의 균형도 필요하다.
- 두 축: **용량 기준**(monitor.log 10MB 넘으면 회전, 10개 유지 — 스크립트 내장) + **시간 기준**(7일 지난 `.log` 압축·아카이브, 30일 지난 `.gz` 삭제 — log_retention.sh). gzip 은 텍스트 로그를 90% 이상 줄여 "오래 보관하되 공간은 적게" 를 만족한다.

## B. 심화 · 꼬리 질문

**B1. `sshd_config` 를 고쳤는데 적용이 안 됐다. 어디를 보나?**
`sshd -T` 로 유효 설정을 본다. Ubuntu 22.04 는 `Include /etc/ssh/sshd_config.d/*.conf` 가 **첫 줄**이고 sshd 는 같은 키의 **첫 값**을 채택하므로 drop-in 이 이긴다. 또 22.10+ 는 `ssh.socket` 이 포트를 소유해 `systemctl restart ssh.socket` 이 필요하다.

**B2. 포트를 바꾸면 보안이 "진짜" 좋아지나?**
근본적 방어(인증 강도)는 그대로다. 그러나 자동화 공격의 노이즈를 제거해 **탐지 가능성**을 높이고, 알려진 포트 기반 취약점 스캐너를 피한다. "계층 방어"의 한 층일 뿐 키 인증·fail2ban·방화벽과 함께 써야 한다.

**B3. UFW `default deny incoming` 상태에서 SSH 응답 패킷은 어떻게 나가나?**
UFW(netfilter) 는 **stateful** 이다. 허용된 인바운드 연결의 응답은 conntrack 이 ESTABLISHED 로 추적해 자동 허용된다. 아웃바운드 default allow 는 서버가 **먼저 시작하는** 연결(apt, DNS)을 위한 것.

**B4. 그룹에 추가했는데 `Permission denied` 가 계속 난다.**
그룹 멤버십은 **로그인 시점**에 프로세스에 부여된다. 이미 열린 셸은 모른다. `su - user` 로 다시 들어가거나 `newgrp`. cron 은 매번 새로 로그인하는 셈이라 바로 반영된다.

**B5. `chmod 770` 으로 충분한데 왜 ACL 을 쓰나?**
단일 그룹이면 충분하다. ACL 이 필요한 순간은 ① 한 디렉토리에 두 그룹 이상 다른 권한 ② 상위 디렉토리 "통과만" ③ `default ACL` 로 새 파일 상속 ④ 특정 사용자 1명 예외. 이 미션에선 AGENT_HOME(core 소유)에 common 통과 권한을 주는 ②, 상속 ③ 때문에 썼다. ACL 은 `ls -l` 에 `+` 로만 보이므로 반드시 `getfacl` 로 확인한다.

**B6. setgid 비트(2770)는 무엇을 하나?**
디렉토리에 setgid 가 있으면 그 안에 **새로 만든 파일/디렉토리의 그룹이 디렉토리의 그룹**이 된다(만든 사람의 기본 그룹이 아니라). 공유 디렉토리에서 "내가 만든 파일을 동료가 못 읽는" 문제를 막는다. 파일의 setgid 는 실행 시 그룹 권한 승격이라 의미가 다르다.

**B7. 디렉토리의 r, w, x 는 각각 무슨 뜻인가?**
r = 항목 이름 목록(ls), x = 통과/진입(cd, 경로 해석), w = 항목 생성·삭제·이름 변경(x 와 함께). **파일 삭제 권한은 파일이 아니라 디렉토리의 w** 라서, AGENT_HOME 에 common 에게 w 를 주면 test 가 api_keys 디렉토리를 옮길 수 있다 → `--x` 만 준 이유.

**B8. `pgrep -f` 의 함정은?**
`-f` 는 전체 명령줄을 정규식으로 매칭하므로 `bash monitor.sh` 자신이나 `vi agent_app.py` 같은 무관한 프로세스가 걸릴 수 있다. 스크립트는 자기 PID 와 부모 PID 를 제외하고, 포트 LISTEN 까지 함께 확인해 오탐을 줄인다. 더 엄격히 하려면 PID 파일이나 systemd 유닛으로 관리한다.

**B9. CPU 사용률을 `/proc/stat` 로 두 번 읽어 빼는 이유는?**
`/proc/stat` 의 값은 **부팅 이후 누적 jiffies** 라 한 번 읽으면 "지금"이 아니라 "부팅 후 평균"이다. 1초 간격 두 샘플의 차이로 현재 구간 사용률을 구한다. `top -bn1` 의 첫 화면도 같은 이유로 부정확하고 출력 형식이 로캘에 따라 달라 파싱이 깨진다.

**B10. MEM 을 `MemAvailable` 로 계산하는 이유는? `free` 의 used 와 다르다.**
Linux 는 남는 메모리를 페이지 캐시로 적극 사용하므로 `MemTotal - MemFree` 는 과대평가다. `MemAvailable`(커널 3.14+) 은 "캐시를 회수하면 쓸 수 있는 양"을 커널이 계산한 값이라 실제 압박을 반영한다. `free` 의 `available` 열과 같다.

**B11. Health Check 실패를 왜 exit 1 로, 임계값 초과는 왜 exit 0 으로 두나?**
종료 코드는 상위 시스템(cron, systemd, 알림)에 대한 **계약**이다. "서비스가 죽었다"(즉시 조치)와 "부하가 높다"(관찰)는 긴급도가 다르다. 둘 다 1 이면 호출자는 구분할 수 없고, 경고 때문에 매분 "실패" 알림이 울려 진짜 장애를 놓친다(alert fatigue).

**B12. cron 에서 되는데 수동 실행은 되고, 혹은 그 반대인 이유?**
환경 차이: cron 은 PATH=`/usr/bin:/bin`, HOME 과 셸(`/bin/sh`)이 다르고 TTY 가 없으며 profile 을 안 읽는다. 그래서 절대경로·환경 파일 source·`#!/usr/bin/env bash` 가 필요하다. 반대로 수동 실행은 되는데 cron 이 안 되면 stderr 를 파일로 받아 보라(`2>>monitor.cron.log`).

**B13. logrotate 대신 스크립트 안에서 회전하는 이유?**
logrotate 는 보통 `cron.daily` 로 하루 한 번 돌아 "10MB 넘는 즉시"를 보장하지 않는다. 또 외부 데몬 설정 의존이 생긴다. 반대로 logrotate 는 `copytruncate`, `postrotate` 훅 등 성숙한 기능이 있어 실무에서는 표준. 미션은 "방법 자유"라 둘 다 유효하며, 저장소는 스크립트 회전을 기본으로 하고 logrotate 설정 예시를 문서에 포함했다.

**B14. `find -mtime +7` 은 7일 이상인가?**
아니다. `-mtime +N` 은 "N+1 일 이상 전"(정수 일 단위 내림 후 N 초과). 7일 이상은 `+6`. 스크립트는 `DAYS-1` 로 변환한다. 경계가 중요하면 `-mmin` 이나 `-newermt` 를 쓴다.

**B15. Boot `[1/5]` 가 왜 root 를 거부하나?**
앱이 root 로 돌면 코드 취약점 하나가 곧 시스템 전체 장악이다. 전용 서비스 계정(agent-admin)으로 돌리면 피해가 그 계정의 권한(upload_files, 로그)으로 한정된다. 실무에선 `systemd` 유닛의 `User=` 로 강제한다.

## C. 흔한 오개념

| 오개념 | 바로잡기 |
|---|---|
| "`PermitRootLogin no` 면 root 계정 자체가 잠긴다" | SSH **원격** 로그인만 막는다. 콘솔 로그인·`sudo -i`·`su -` 는 그대로. |
| "포트만 바꾸면 안전하다" | 스캐너는 전체 포트를 훑는다. 키 인증·방화벽·fail2ban 과 함께 써야 한다. |
| "UFW 를 enable 하면 기존 연결도 끊긴다" | 기존 ESTABLISHED 세션은 유지된다(conntrack). 새 연결만 규칙을 탄다. 다만 20022 를 안 열었으면 **다음** 접속부터 막힌다. |
| "`chmod 770` 디렉토리는 그룹원이 안의 파일을 다 읽을 수 있다" | 파일 자체의 권한도 봐야 한다. 디렉토리 권한은 목록·통과·생성/삭제만 정한다. |
| "`usermod -aG` 하면 즉시 반영된다" | 새 로그인부터. 열려 있는 셸은 재로그인. |
| "ACL 은 `ls -l` 에 나온다" | `+` 표시만 나온다. `getfacl` 로 봐야 한다. 그리고 ACL 의 `mask` 가 실효 권한 상한이다. |
| "cron 이 `* * * * *` 면 정확히 60초 간격" | 매 분의 **0초**에 시작한다. 실행에 1초 넘게 걸려도 다음 분 0초에 또 시작(겹칠 수 있다). |
| "`su user` 와 `su - user` 는 같다" | `-` 가 있어야 로그인 셸 → `/etc/profile.d` 가 읽혀 AGENT_* 가 잡힌다. |
| "MEM 사용률 = (Total-Free)/Total" | 캐시 때문에 과대. `MemAvailable` 기준이 맞다. |
| "exit 1 이면 cron 이 재시도한다" | cron 은 재시도하지 않는다. 종료 코드는 메일(MTA 있을 때)과 로그로만 남는다. 재시도/재기동은 systemd 나 감시 도구의 몫. |
| "로그는 많이 남길수록 좋다" | 보존 정책 없는 로그는 디스크 풀 장애의 1위 원인. 용량·시간 기준 회전과 삭제가 필요하다. |

## D. 실무 시나리오

**D1. 새벽 3시에 앱이 죽었다는 신고. 어디서부터 보나?**
① `tail /var/log/agent-app/monitor.error.log` → 첫 `HEALTH_CHECK_FAIL` 시각 = 죽은 시각 상한. ② 그 직전 `monitor.log` 구간을 `report.sh --from --to` 로 요약 → CPU/MEM 추세(OOM?), DISK(풀?). ③ PID 열이 바뀐 시각 = 재시작 이력. ④ `journalctl`/앱 로그와 교차. ⑤ 조치 후 cron 이 다시 `[OK]` 줄을 쓰는지 확인. 로그가 없었다면 "감"으로 시작했을 일이다.

**D2. agent-test 가 "업로드 폴더에 파일을 올렸는데 dev 가 못 읽는다"고 한다.**
`ls -l` 로 그룹 확인. `agent-test` 그룹이면 setgid/default ACL 이 빠진 것. `chmod g+s`, `setfacl -d -m g:agent-common:rwx`, 기존 파일은 `chgrp agent-common`. 원인 설명과 함께 설정 스크립트에 반영(재발 방지).

**D3. 운영자가 퇴사했다. 무엇을 바꾸나?**
개인 계정 잠금(`usermod -L`), 그의 SSH 키 제거, `api_keys` 내용 **교체**(열람 가능했던 비밀은 유출 가정), cron 은 역할 계정(agent-admin)이라 그대로 동작. 역할 기반 설계 덕에 서비스는 영향이 없다.

**D4. monitor.log 가 하루 만에 10MB 를 넘는다.**
한 줄 ~60B × 1,440줄/일 ≈ 86KB 라 정상이면 불가능. 누군가 stdout 전체를 로그로 리다이렉트했거나 포맷이 바뀌었다. `head`로 내용 확인 → crontab 의 리다이렉션 수정. 회전 로직 덕에 디스크는 최대 100MB 로 제한됐다는 점이 보존 정책의 가치.

**D5. CPU 경고가 매분 뜬다. 임계값을 올릴까?**
먼저 원인(`top`, `ps -eo pid,pcpu,cmd --sort=-pcpu | head`). 상시 부하가 정상이면 임계값을 SLO 에 맞춰 조정하되 **변경 사유를 기록**. 노이즈 경고를 방치하면 진짜 경고를 무시하게 된다.

**D6. 방화벽을 firewalld 로 바꿔야 한다면?**
`systemctl disable --now ufw` → `dnf/apt install firewalld` → `firewall-cmd --permanent --add-port=20022/tcp --add-port=15034/tcp` → `--remove-service=ssh`(22) → `--reload` → `firewall-cmd --list-all`. monitor.sh 는 `firewall-cmd --state` 로 자동 감지한다.

## E. monitor.sh 코드 리뷰형 질문

**E1. `set -e` 를 안 쓴 이유?**
Health Check 의 실패는 **의도된 분기**이고 `grep` 의 "없음"(exit 1) 처럼 실패가 정상인 명령이 많다. `set -e` 는 이런 곳에서 예기치 않게 종료시킨다. 대신 `set -u`(미정의 변수 차단), `set -o pipefail` 과 **명시적 종료 코드**를 쓴다.

**E2. 환경 변수로 입력 파일(`MONITOR_PROC_STAT`)을 바꿀 수 있게 한 이유?**
테스트 가능성. 실제 `/proc` 없이도(macOS, CI) CPU 25.3% 같은 **결정적 입력**으로 임계값 로직을 검증한다. 운영에서는 기본값(`/proc/stat`)만 쓴다.

**E3. Health Check 실패를 왜 monitor.log 가 아닌 monitor.error.log 에 쓰나?**
monitor.log 는 한 줄 고정 포맷이라 report.sh 와 grep 이 그대로 집계한다. 다른 포맷의 줄을 섞으면 파서가 복잡해진다. 실패 시각은 별도 파일에 남겨 추적성은 유지한다.

**E4. 10MB 검사는 어디서 하나? 경쟁 조건은?**
append 직전에 `wc -c` 로 검사 후 `mv` 회전. 수동 실행과 cron 이 겹치면 둘 다 크기 검사를 통과해 같은 초에 회전할 수 있으므로, 시작 시 로그 디렉토리의 `.monitor.lock` 에 `flock` 을 건다(5초 대기 후 실패 시 exit 1). `flock` 이 없는 환경(macOS)에서는 생략한다.

**E5. 왜 `ss -tlnH` 에서 `$4 ~ ":15034$"` 로 매칭하나?**
`-H` 로 헤더를 빼면 4번째 열이 `Local Address:Port`. `0.0.0.0:15034`, `[::]:15034`, `*:15034` 모두 끝이 `:15034` 라 하나의 정규식으로 잡힌다. `grep 15034` 만 쓰면 `:150340` 이나 Peer 열에 우연히 걸릴 수 있다.

**E6. 코드 리뷰에서 무엇이 잡혔고 어떻게 고쳤나?**
① cron/`su -` 의 PATH 에 `/usr/sbin` 이 없어 `ufw` 를 못 찾고 "no firewall" 로 오판 → 스크립트가 PATH 에 sbin 을 덧붙임. ② `pgrep -f` 가 `vim agent_app.py` 같은 프로세스에 오탐 → 포트를 LISTEN 하는 PID 를 우선. ③ 비root 에서 매분 `sudo -n` 시도 → auth.log 오염이라 제거. ④ 보존 스크립트가 같은 이름의 아카이브를 덮어쓰고, gzip 이 mtime 을 유지해 30일 삭제가 즉시 발동 → 타임스탬프 접미사 + mtime 갱신. ⑤ `report.sh --from`(값 없음) 무한 루프 → 인자 수 검사. ⑥ SSH 설정 스크립트의 잠금 위험(22 규칙을 먼저 지움, 문법 오류 시 설정이 남음, root 직접 접속 중 실행) → 순서 변경·자동 복원·실행 거부. ⑦ 보조 로그 무한 증가 → 같은 기준으로 회전.

**E7. 테스트는 무엇을 검증하나?**
단위 86건: 정상/실패 종료 코드, 로그 포맷 정규식, 임계값 경계(20.0 은 경고 없음), 10MB 회전과 10개 유지, 권한 오류 메시지, report 집계값·구간 필터·예외 코드, 보존 정책의 7/30일 경계·dry-run·예외. Docker E2E: Ubuntu 22.04 에서 설정 스크립트 → 권한 실동작 → 앱 기동 → cron 누적까지. (E2E 가 mawk 정규식 호환 버그를 실제로 잡았다.)
