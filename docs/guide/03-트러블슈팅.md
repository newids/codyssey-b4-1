# 트러블슈팅 — 증상 → 원인 → 확인 → 조치

> 수행 내역서에 "겪은 문제" 절을 넣을 때 아래 형식(증상/원인/확인 명령/조치/재발 방지)으로 쓰면 좋다.

## T1. sshd 포트를 바꿨는데 여전히 22 에서 리슨한다
- **증상**: `ss -tulnp | grep sshd` 에 `:22` 가 남아 있고 `:20022` 가 없다.
- **원인**: Ubuntu 22.10+/24.04 는 `ssh.socket`(systemd 소켓 활성화)이 포트를 소유한다. `sshd_config` 의 `Port` 는 소켓 단위에 반영되지 않는다. 22.04 는 `ssh.service` 라 해당 없음.
- **확인**: `systemctl is-enabled ssh.socket`, `systemctl cat ssh.socket`
- **조치**: `sudo systemctl daemon-reload && sudo systemctl restart ssh.socket ssh` (24.04 는 `sshd_config` 의 Port 를 generator 가 소켓에 반영한다. 안 되면 `systemctl disable --now ssh.socket && systemctl enable --now ssh`)
- **재발 방지**: `scripts/setup/01-ssh-firewall.sh` 가 socket 여부를 보고 두 경우를 모두 처리.

## T2. `PermitRootLogin no` 로 바꿨는데 root 로 로그인된다
- **원인**: `/etc/ssh/sshd_config.d/*.conf` 가 `Include` 로 **먼저** 읽히고, sshd 는 같은 키는 **첫 값**을 쓴다.
- **확인**: `sudo sshd -T | grep -i permitrootlogin`, `grep -Rn PermitRootLogin /etc/ssh/sshd_config.d/`
- **조치**: drop-in 의 값을 `no` 로 바꾸거나 주석 처리 후 재시작.
- **교훈**: 설정 파일을 grep 한 결과와 **유효(effective) 설정** 은 다를 수 있다. 증빙은 `sshd -T` 로.

| [2/5] Env | `su agent-admin`(`-` 없음) 이라 profile.d 미적용 / 변수 오타 | `env | grep AGENT_` | `su - agent-admin` 또는 `. /etc/profile.d/agent-env.sh` |
| [3/5] Files | 키 파일 경로 다름, 내용에 공백/따옴표, 줄 2개, 읽기 권한 없음 | `cat -A $AGENT_KEY_PATH`, `ls -l` | `printf 'agent_api_key_test\n' > …`, `chmod 660`, 그룹 agent-core |
| [4/5] Port | 이전 앱/mock 이 15034 점유 | `ss -tlnp | grep 15034` | 해당 PID 종료 |
| [5/5] Log | agent-admin 이 agent-core 가 아님(새 그룹은 재로그인 후 반영), 디렉토리 권한 | `id`, `getfacl /var/log/agent-app`, `touch /var/log/agent-app/x` | `usermod -aG` 후 **재로그인**, ACL 재설정 |

## T4. agent-test 가 upload_files 에 접근하지 못한다 (Permission denied)
- **원인**: 경로상의 **모든 상위 디렉토리에 x(통과) 권한**이 필요하다. `/home/agent-admin` 은 Ubuntu 22.04 기본 750 이고 `$AGENT_HOME` 도 750 이라 agent-common 이 통과를 못 한다.
- **확인**: `sudo -u agent-test namei -l /home/agent-admin/agent-app/upload_files`
- **조치**: `setfacl -m g:agent-common:--x /home/agent-admin /home/agent-admin/agent-app`
- **왜 rwx 가 아니라 --x 인가**: 디렉토리 쓰기 권한은 "그 안의 항목 삭제/이름 변경" 권한이다. AGENT_HOME 을 common 에 쓰기로 열면 test 가 `api_keys` 디렉토리를 통째로 옮길 수 있다.

## T5. 새로 만든 파일을 같은 그룹 사람이 못 읽는다
- **원인**: 파일의 그룹이 만든 사람의 기본 그룹(`agent-dev`)이 됨. setgid 비트가 없거나 default ACL 이 없다.
- **확인**: `ls -l` 의 그룹 열, `getfacl` 의 `default:` 줄, `ls -ld` 의 `s`
- **조치**: `chmod g+s 디렉토리`, `setfacl -d -m g:agent-common:rwx 디렉토리`. 이미 만들어진 파일은 `chgrp -R`.

## T6. cron 은 등록했는데 monitor.log 가 늘지 않는다
순서대로 확인한다.
1. cron 이 실행은 했나: `grep CRON /var/log/syslog | tail` 또는 `journalctl -u cron -n 20`. 줄이 없으면 `systemctl status cron`.
2. 실행은 했는데 실패: `cat /var/log/agent-app/monitor.cron.log`, `tail /var/log/agent-app/monitor.error.log`
   - `HEALTH_CHECK_FAIL process ... not running` → 앱이 꺼져 있다(정상 동작: exit 1 이면 로그를 안 쓴다). 앱을 띄운다.
   - `Permission denied` → agent-admin 의 그룹/ACL (T3 [5/5] 와 동일).
   - `command not found` → cron 의 PATH 는 `/usr/bin:/bin`. 스크립트 안에서 절대경로를 쓰거나 PATH 지정.
3. `%` 문자: crontab 에서 `%` 는 줄바꿈으로 해석된다. 명령에 `date +%F` 같은 걸 넣었다면 `\%` 로 이스케이프.
4. 새 그룹 반영: `usermod -aG` 직후 cron 은 새 그룹을 알지만, 이미 열려 있던 셸은 모른다. `su - agent-admin` 으로 다시 들어가 `id` 확인.

## T7. monitor.sh 의 CPU 가 항상 0.0% 또는 100%
- **0.0%**: 1초 샘플 사이 거의 유휴(정상). 부하를 줘서 확인: `yes > /dev/null &` 후 실행, 끝나면 `kill %1`.
- **100%/이상값**: `/proc/stat` 첫 줄 열 수가 커널마다 다르지만 스크립트는 `NF` 까지 모두 합산하므로 문제없다. 컨테이너에서 호스트 전체 CPU 를 읽는 것은 정상.
- **MEM 이 예상과 다름**: 스크립트는 `MemAvailable` 기준(커널이 계산한 실사용). `free -m` 의 `used` 와는 버퍼/캐시 차이가 있다.

## T8. ufw 를 켰더니 SSH 가 끊겼다 / 새 접속이 안 된다
- **원인**: `ufw allow 20022/tcp` 전에 `enable` 했거나, 클라우드 보안그룹에서 20022 를 안 열었다.
- **조치**: 콘솔(VM 화면/클라우드 시리얼 콘솔)로 들어가 `ufw allow 20022/tcp`. 클라우드면 보안그룹 추가.
- **예방**: 항상 `allow → enable → 다른 터미널로 접속 확인 → 기존 세션 종료` 순서.

## T8-1. `01-ssh-firewall.sh` 가 "root 로 직접 SSH 접속한 세션" 이라며 멈춘다
- **원인**: 의도된 안전장치. `PermitRootLogin no` 가 적용되는 순간 root 로는 다시 못 들어온다.
- **조치**: `adduser ops && usermod -aG sudo ops` 후 키/비밀번호를 설정하고 `ssh ops@host` 로 들어와 `sudo` 로 실행. 정말 다른 계정이 준비돼 있다면 `--force`.

## T9. 컨테이너(Docker)에서 ufw enable 이 실패한다
- **원인**: iptables/nftables 를 조작할 `CAP_NET_ADMIN` 이 없다. 컨테이너 제약이지 설정 오류가 아니다.
- **조치**: UFW 증빙은 VM 에서 수행. monitor.sh 는 비활성 상태를 `[WARNING]` 으로만 보고하므로 나머지 검증은 컨테이너로 가능(`tests/integration/docker-e2e.sh`).

## T10. `ufw status` 가 "You need to be root" 라고 한다 (monitor.sh 를 일반 계정으로 실행)
- **원인**: `ufw status` 는 root 전용.
- **조치**: monitor.sh 는 root 가 아니면 `systemctl is-active ufw` + `/etc/ufw/ufw.conf` 의 `ENABLED=yes` 로 판단한다(둘 다 비root 로 읽을 수 있다). 매분 `sudo -n` 을 시도하는 방식은 실패할 때마다 `auth.log` 에 "NOT in sudoers" 가 하루 1,440줄 쌓이므로 쓰지 않았다.
- **PATH 함정**: cron 과 `su -` 의 PATH 에는 `/usr/sbin` 이 없어 `command -v ufw` 가 실패하고 "no firewall found" 가 찍힌다. monitor.sh 는 시작 시 sbin 경로를 PATH 에 덧붙여 해결한다.

## T11. report.sh 가 "no samples found" 만 출력한다
- **원인 1**: Ubuntu 기본 awk(mawk)가 `{n}` 수량자를 지원하지 않아 패턴이 아무 줄도 못 잡았다 → 현재 버전은 수정됨.
- **원인 2**: `--from/--to` 형식 오류(`2026/02/25` 등) → `YYYY-MM-DD HH:MM:SS`.
- **확인**: `MONITOR_LOG_FILE=/var/log/agent-app/monitor.log bash -x report.sh 2>&1 | head`

## T12. 로그 회전 뒤 cron 이 찍는 줄이 사라진 것처럼 보인다
- **원인**: 10MB 도달 시 `monitor.log` 가 `monitor.YYYYmmdd_HHMMSS.log` 로 이름이 바뀌고 새 파일이 시작된다. `tail -f` 로 보고 있었다면 옛 파일을 따라간 것.
- **조치**: `tail -F`(대문자) 사용. `ls -lt /var/log/agent-app/` 로 회전본 확인.
