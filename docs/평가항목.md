# B4-1 평가항목과 모범 답안

각 질문 아래 답안은 소리 내어 말할 수 있게 3~5줄로 썼다. 답안은 이 저장소의 실제 구현(`scripts/monitor.sh`, `scripts/setup/*.sh`)을 기준으로 한다.
항목 1은 직접 보여 줘야 하는 항목이라 답안 뒤에 확인 명령을 한 줄씩 붙였다.

---

## 항목 1. 구현 결과 확인

### 1-1. SSH 포트가 20022로 변경되었고, Root 원격 접속이 차단되는가?

네. `/etc/ssh/sshd_config`에서 `Port 20022`, `PermitRootLogin no`로 바꾸고 sshd를 재시작했습니다.
바꾸기 전에 설정 파일을 백업했고, `sshd -t`로 문법을 먼저 검사해서 접속이 끊기는 사고를 막았습니다.
지금 20022번으로 일반 계정은 접속되고, root로 접속하면 Permission denied가 나옵니다.

확인: `sshd -T | grep -Ei '^(port|permitrootlogin) '`, `ssh -p 20022 root@<host>`

### 1-2. 방화벽이 활성화되어있고(택1: UFW 또는 Firewalld), 20022/tcp와 15034/tcp만 허용되는가?

UFW를 선택했습니다. 들어오는 연결은 기본 차단으로 두고, SSH용 20022/tcp와 앱용 15034/tcp 두 개만 허용했습니다.
기존 22번 규칙은 sshd가 20022에서 듣고 있는 것을 확인한 다음에 지웠습니다.
순서를 이렇게 잡은 이유는, 새 포트가 열리기 전에 22번을 막으면 서버에 다시 들어올 수 없기 때문입니다.

확인: `sudo ufw status verbose`

### 1-3. agent-admin/dev/test 계정과 agent-common/core 그룹이 요구사항대로 구성되어있는가?

계정 세 개와 그룹 두 개를 만들었습니다.
agent-common에는 admin, dev, test 세 명이 모두 들어가고, agent-core에는 admin과 dev만 들어갑니다.
그래서 upload_files는 세 명 모두 읽고 쓸 수 있고, api_keys와 로그 디렉토리는 core 두 명만 접근할 수 있습니다.
agent-test는 core에 없기 때문에 키 파일과 로그를 열 수 없습니다.

확인: `id agent-admin; id agent-dev; id agent-test`, `getent group agent-common agent-core`

### 1-4. 앱이 Boot Sequence 5단계 [OK]를 통과하고 "Agent READY"가 출력되는가?

네. 앱은 시작할 때 환경 변수, 디렉토리, 키 파일, 포트 같은 조건을 순서대로 검사합니다.
그래서 환경 변수를 `/etc/profile.d/agent-env.sh`에 고정하고, 키 파일을 `api_keys/secret.key`에 만들어 두었습니다.
미션 문서에는 `t_secret.key`로 적혀 있지만, 제공된 앱을 실제로 실행해 보니 `AGENT_KEY_PATH`를 키 디렉토리(`api_keys`)로 보고 그 안의 `secret.key`를 찾아서 앱 동작에 맞췄습니다.
agent-admin으로 로그인해서 앱을 실행하면 5단계가 모두 [OK]로 나오고 마지막에 Agent READY가 출력됩니다.
그 뒤 15034 포트가 LISTEN 상태인 것도 확인했습니다.

확인: agent-admin으로 앱 실행 후 `ss -tlnp | grep 15034`

### 1-5. monitor.sh가 프로세스/포트 상태를 점검하고, 비정상 상태에서 exit 1로 종료되는가?

네. 먼저 앱 프로세스가 떠 있는지 보고, 그다음 15034 포트가 LISTEN 중인지 봅니다.
둘 중 하나라도 실패하면 [FAIL] 메시지를 출력하고 바로 exit 1로 끝납니다.
이때는 monitor.log에 줄을 쓰지 않고, 실패 이유만 monitor.error.log에 따로 남깁니다.
앱을 끄고 스크립트를 실행한 뒤 `echo $?`를 하면 1이 나오는 것으로 확인할 수 있습니다.

확인: 앱 종료 → `monitor.sh; echo $?`

### 1-6. /var/log/agent-app/monitor.log가 지정 포맷으로 누적 기록되는가?

네. 한 번 실행할 때마다 한 줄씩 추가됩니다.
형식은 `[날짜 시간] PID:번호 CPU:값% MEM:값% DISK_USED:값%`입니다.
`>>`로 이어 쓰기 때문에 이전 기록이 지워지지 않고 계속 쌓입니다.

확인: `tail -n 5 /var/log/agent-app/monitor.log`

### 1-7. cron 매분 실행으로 monitor.log가 자동 증가하는가?

네. agent-admin의 crontab에 `* * * * *`로 등록했습니다.
cron은 로그인할 때의 환경 변수를 물려받지 않기 때문에, 환경 변수 파일을 먼저 읽은 다음 monitor.sh를 실행하게 했습니다.
1분 간격으로 `tail`을 두 번 해 보면 줄이 하나 늘어난 것을 볼 수 있습니다.

확인: `crontab -l -u agent-admin`, `wc -l monitor.log; sleep 65; wc -l monitor.log`

### 1-8. monitor.log 용량관리(10MB/10개)가 설정되어 있고 동작을 설명할 수 있는가?

monitor.sh 안에 직접 구현했습니다. 로그를 쓰기 직전에 파일 크기를 확인합니다.
10MB를 넘었으면 기존 파일 이름에 날짜와 시간을 붙여서 옮기고, 새 monitor.log에 쓰기 시작합니다.
옮겨 둔 파일은 최신 9개만 남기고 오래된 것부터 지웁니다.
그래서 현재 파일 1개와 보관본 9개, 합쳐서 최대 10개, 약 100MB까지만 차지합니다.

확인: `ls -lh /var/log/agent-app/`

## 항목 2. 구현 방식 설명

### 2-1. monitor.sh에서 프로세스 식별(pgrep/ps 등)과 포트 확인(ss/netstat 등)에 사용한 명령과 선택 이유를 설명할 수 있는가?

프로세스는 `pgrep -f`로 찾았습니다. 명령줄 전체에서 앱 이름을 찾아 PID만 돌려주기 때문에, `ps | grep`처럼 grep 자신이 걸리는 문제가 없습니다.
후보가 여러 개면 실제로 15034 포트를 열고 있는 PID를 우선으로 골라서 잘못 잡는 경우를 줄였습니다.
포트는 `ss -tln`으로 확인했습니다. 요즘 리눅스에 기본으로 들어 있고 netstat보다 빠릅니다.
ss가 없는 환경을 대비해 netstat, 그것도 없으면 `/dev/tcp` 연결 시도 순서로 대체하도록 했습니다.

### 2-2. CPU/MEM/DISK 값을 어떤 방식으로 추출/파싱했고, 로그/포맷을 왜 그 형태로 고정했는지 설명할 수 있는가?

CPU는 `/proc/stat`을 1초 간격으로 두 번 읽어서, 그 사이에 일한 시간의 비율을 계산했습니다.
메모리는 `/proc/meminfo`의 MemTotal과 MemAvailable로 사용률을 구했고, 디스크는 `df -P /`의 사용률 칸에서 %를 떼어 냈습니다.
top이나 free의 출력은 버전과 언어 설정에 따라 모양이 달라지는데, /proc 파일과 `df -P`는 형식이 일정해서 awk로 안정적으로 뽑을 수 있습니다.
로그 형식을 한 줄, 고정된 `키:값` 형태로 정한 이유는 나중에 grep이나 awk로 통계를 내기 쉽게 하기 위해서입니다. 실제로 report.sh가 이 형식을 읽어 평균과 최대값을 계산합니다.

### 2-3. 소유자(agent-dev)와 실행자(agent-admin, cron) 권한 정책을 어떻게 만족시켰는지(소유/그룹/권한) 설명할 수 있는가?

monitor.sh의 소유자는 agent-dev, 그룹은 agent-core, 권한은 750으로 두었습니다.
750이면 소유자인 dev는 읽기·쓰기·실행이 모두 되고, 그룹은 읽기와 실행만 되고, 그 밖의 사용자는 아무것도 못 합니다.
agent-admin은 agent-core 그룹이라서 실행은 되지만 내용을 고칠 수는 없습니다.
즉 스크립트를 만드는 사람과 돌리는 사람을 나눈 것이고, cron도 agent-admin의 crontab에 등록해서 같은 권한으로 돌아갑니다.

### 2-4. 용량 기반 로그 관리(10MB/10개)를 어떤 방식(logrotate/스크립트)으로 구현했는지 설명할 수 있는가?

logrotate가 아니라 monitor.sh 안의 함수로 구현했습니다.
logrotate는 보통 하루에 한 번 root 권한으로 돌기 때문에, 그 사이에 10MB를 넘어도 바로 처리되지 않습니다.
스크립트 방식은 매분 로그를 쓰기 직전에 크기를 보므로 기준을 넘으면 바로 회전하고, root 권한 없이 agent-admin 권한만으로 동작합니다.
`wc -c`로 크기를 재고, `mv`로 이름을 바꾸고, `ls -t`로 최신순 정렬해서 10개째부터 삭제합니다.
수동 실행과 cron이 겹치는 경우에 대비해 flock으로 동시에 회전하지 않게 막았습니다.

## 항목 3. 원리 이해

### 3-1. SSH 포트 변경과 Root 접속 차단이 왜 보안에 효과적인지 위협 모델 관점에서 설명할 수 있는가?

가장 흔한 위협은 인터넷 전체를 훑으며 22번 포트에 비밀번호를 무작위로 넣어 보는 자동화 봇입니다.
포트를 20022로 바꾸면 이런 봇의 대부분이 서버를 찾지 못해서 공격 시도와 로그 소음이 크게 줄어듭니다. 다만 포트 스캔을 하면 찾을 수 있으니 숨기는 효과일 뿐 완전한 방어는 아닙니다.
root는 모든 리눅스에 있는 계정이라 공격자가 아이디를 맞힐 필요가 없고, 뚫리면 서버 전체를 잃습니다.
root 접속을 막으면 공격자는 계정 이름부터 알아내야 하고, 뚫더라도 일반 계정 권한에서 멈춥니다. 관리자는 sudo를 쓰게 되어 누가 무엇을 했는지 기록도 남습니다.

### 3-2. api_keys와 로그 디렉토리를 agent-core로 제한한 이유를 "최소 권한 원칙"으로 설명할 수 있는가?

최소 권한 원칙은 각 계정에 일에 꼭 필요한 권한만 주는 것입니다.
API 키는 유출되면 바로 악용될 수 있고, 로그에는 PID나 시스템 상태 같은 내부 정보가 들어 있습니다.
이것을 다뤄야 하는 사람은 운영자인 admin과 개발자인 dev뿐이고, 테스트 계정은 파일 업로드만 하면 됩니다.
그래서 test 계정이 탈취되거나 실수를 하더라도 키와 로그까지는 피해가 번지지 않습니다.
디렉토리에 setgid와 기본 ACL을 걸어서, 나중에 새로 생기는 파일도 같은 제한을 자동으로 물려받게 했습니다.

### 3-3. "경고는 출력하되 종료하지 않는 항목"(방화벽 비활성/임계치 초과)을 분리한 운영상의 이유를 설명할 수 있는가?

두 종류는 심각도가 다릅니다. 프로세스가 죽었거나 포트가 닫힌 것은 서비스가 멈춘 장애라서 exit 1로 끝냅니다.
반면 방화벽이 꺼져 있거나 CPU가 높은 것은 서비스는 돌아가고 있지만 주의가 필요한 상태입니다.
이때 스크립트를 종료해 버리면 그 시점의 수치가 로그에 남지 않아서, 정작 문제가 생긴 순간의 기록이 비게 됩니다.
그래서 경고만 출력하고 수집과 기록은 끝까지 진행합니다. 종료 코드는 진짜 장애에만 쓰기 때문에 알림이 너무 자주 울려 무시당하는 일도 막을 수 있습니다.

### 3-4. 리다이렉션 기호 >와 >>의 차이를 설명하고, 로그 누적에 >>가 필요한 이유를 설명할 수 있는가?

`>`는 파일을 비우고 처음부터 새로 씁니다. `>>`는 기존 내용을 그대로 두고 맨 끝에 덧붙입니다.
로그는 시간이 지나며 어떻게 변했는지를 보기 위한 기록이라서 이전 줄이 남아 있어야 합니다.
만약 `>`를 쓰면 매분 실행될 때마다 파일이 덮어써져서 항상 마지막 한 줄만 남습니다.
그래서 monitor.sh는 `>>`로 한 줄씩 추가하고, 대신 무한히 커지지 않도록 10MB 회전으로 크기를 관리합니다.

## 항목 4. 응용과 장애 대응

### 4-1. 모니터링 대상이 웹 서버(Nginx 등)로 바뀐다면, monitor.sh에서 바꿔야 할 핵심 포인트(프로세스/포트/로그/임계값)를 설명할 수 있는가?

네 가지를 바꿉니다. 이 값들은 스크립트 위쪽에 환경 변수로 모아 두어서 본문 로직은 거의 고칠 필요가 없습니다.
프로세스는 이름을 nginx로 바꾸되, nginx는 master와 worker 여러 개가 뜨므로 master PID를 기준으로 잡습니다.
포트는 15034 대신 80과 443을 확인하고, 방화벽 허용 포트도 같이 바꿉니다.
로그는 경로를 `/var/log/nginx` 쪽으로 옮기고, 필요하면 access.log의 5xx 응답 수 같은 웹 서버 지표를 추가합니다.
임계값은 웹 서버의 평소 부하에 맞춰 다시 정하고, 포트가 열려 있어도 응답을 못 하는 경우가 있으니 `curl`로 HTTP 200 응답까지 확인하면 더 정확합니다.

### 4-2. "프로세스는 살아있는데 포트가 안 열리는 상황"을 발견했다면, 원인 후보와 확인 순서를 설명할 수 있는가?

원인 후보는 네 가지입니다. 앱이 아직 초기화 중이거나 멈춰 있는 경우, 다른 프로세스가 포트를 먼저 차지한 경우, 환경 변수가 잘못돼 다른 포트로 뜬 경우, 권한이나 설정 오류로 포트 열기에 실패한 경우입니다.
확인은 이 순서로 합니다. 먼저 `ss -tlnp`로 그 PID가 실제로 어떤 포트를 열고 있는지, 15034를 다른 프로세스가 쓰고 있는지 봅니다.
다음으로 앱 로그에서 bind 실패나 Address already in use 같은 오류를 찾습니다.
그다음 `/proc/PID/environ`으로 실행 당시의 AGENT_PORT 값을 확인하고, 프로세스 상태와 CPU 사용을 보고 멈춰 있는지 판단합니다.
참고로 방화벽은 LISTEN 상태에 영향을 주지 않으므로, 서버 안에서 포트가 안 보이면 방화벽이 아니라 앱 쪽 문제입니다.

### 4-3. 로그가 급증해 디스크가 가득 찰 위험이 있다면, 운영자가 취할 대응(단기/중기)을 설명할 수 있는가?

단기로는 먼저 `df -h`와 `du -sh`로 어느 디렉토리, 어느 파일이 커졌는지 찾습니다.
오래된 로그는 압축하거나 다른 곳으로 옮기고 지웁니다. 지금 쓰이고 있는 파일은 `rm`으로 지워도 프로세스가 붙잡고 있으면 공간이 돌아오지 않으므로 `truncate`로 비웁니다.
그리고 같은 줄이 반복해서 찍히고 있는지 확인해서 급증의 원인을 멈춥니다.
중기로는 회전 기준과 보관 개수를 조정하고, 7일 지난 로그는 압축하고 30일 지난 것은 삭제하는 보존 정책을 자동화합니다. 이 저장소의 `log_retention.sh`가 그 역할을 합니다.
